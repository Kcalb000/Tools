1. 先建立正确的概念

1.1 Git、GitHub、GitHub CLI、Copilot CLI 有什么区别？

名称是什么用途
Git分布式版本控制软件在电脑上记录文件的版本历史、比较改动、创建分支和提交
GitHub基于 Git 的网站和协作平台在线存放仓库、与他人协作、审查改动、管理 Issue 和发布版本
GitHub CLI（gh）GitHub 官方命令行程序在终端创建仓库、管理 PR、Issue、Release 等 GitHub 功能
GitHub Copilot CLI（copilot）AI 命令行助手用自然语言咨询、解释或协助完成终端任务；具体功能取决于安装版本
终端接收文字命令的程序Windows 上可以使用 PowerShell、Windows Terminal 或 Git Bash

记住：git push 是 Git 命令；gh repo create 是 GitHub CLI 命令；copilot 是 Copilot CLI 命令。它们不能互相替代。

1.2 什么是仓库？

仓库（Repository，常简称 repo） 是一个项目文件夹及其版本历史。一个仓库通常包含：

  • 工作文件： 代码、图片、文档、配置等。
  • .git 目录： Git 用来保存本地版本历史和仓库设置的数据。不要手动删除或编辑它。
  • 提交历史： 文件在不同时间点的记录。

同一个仓库可以有多个副本：你电脑上的叫本地仓库，GitHub 上的叫远程仓库。它们不会在每次保存文件时自动同步，需要你明确地拉取或推送。

1.3 Git 的四个区域

工作区                 暂存区                    本地仓库                 GitHub 远程仓库
你正在编辑的文件  --git add-->  下一次提交的候选内容  --git commit-->  本地历史  --git push-->  云端历史
      ^                                                                      |
      |-------------------------- git pull / git fetch ----------------------|
  • 工作区（working tree）： 磁盘上正在查看和编辑的文件。
  • 暂存区（staging area / index）： 准备放进下一次提交的一组改动。它让你可以挑选哪些改动一起保存。
  • 本地仓库： 电脑上的 .git 数据库，保存提交历史。
  • 远程仓库： 例如 GitHub 上的仓库。

最常用的流程是：

编辑文件 → git status 检查 → git add 暂存 → git commit 保存到本地 → git push 上传到 GitHub

1.4 保存、提交、上传不是一回事

  • 在编辑器按 Ctrl+S：只把文件保存到电脑。
  • git add：选择要纳入下一次提交的文件改动。
  • git commit：创建本地历史记录；此时别人还看不到。
  • git push：将本地提交上传到 GitHub。

<strong>记住：</strong>只保存文件不等于上传；提交（commit）也不等于推送（push）。

[!NOTE] 本指南用蓝色标记概念提示、用琥珀色标记操作注意事项、用红色标记可能造成损失的风险。颜色是辅助信息；即使预览器不显示行内颜色，文字标签和 GitHub 提示块仍会说明重点。

2.3 常见命令对比

容易混淆的词区别
git add 与 git commitadd 选择改动；commit 把暂存内容记录到本地历史
commit 与 pushcommit 保存到本地；push 上传本地提交
fetch 与 pullfetch 下载远程更新但不合并进当前分支；pull 通常是下载后再整合
clone 与 forkclone 是下载到电脑；fork 是在 GitHub 上复制到自己的账号
merge 与 rebase都能整合改动；merge 保留分支汇合记录，rebase 重新应用提交并可能改写历史
restore 与 resetrestore 常用于恢复文件或取消暂存；reset 移动当前分支/HEAD，错误用法可能丢失未提交内容
revert 与 resetrevert 生成一个新提交来抵消旧提交，通常适合已推送历史；reset 改写本地分支位置

3. 准备电脑与 GitHub 账号

3.1 需要安装什么？

  1. Git： Windows 用户可从 git-scm.com 安装 Git for Windows；macOS 通常可安装 Xcode Command Line Tools（运行 git --version 时系统可能提示安装），或使用 Homebrew：

``sh xcode-select --install ``

或：

``sh brew install git ``

  1. 终端： Windows 可使用 PowerShell 或 Windows Terminal；macOS 可使用系统自带的 Terminal（终端）应用，也可使用 iTerm2。macOS 默认 shell 通常为 zsh。
  2. GitHub CLI（gh）： GitHub 官方命令行工具。Windows 可在 PowerShell 执行：

``powershell winget install --id GitHub.cli ``

macOS 若已安装 Homebrew，可执行：

``sh brew install gh ``

安装完成后关闭并重新打开终端，再检查：

``powershell git --version gh --version ``

  1. 可选编辑器： 例如 Visual Studio Code。可以在仓库目录运行 code . 打开项目；如果提示找不到 code，可使用编辑器菜单打开文件夹。

3.2 Windows PowerShell 提示

  • PowerShell 的提示符通常以 PS 开头；本指南的主要命令都适用于 PowerShell。
  • 路径有空格或特殊字符时，用引号包起来：

``powershell cd 'C:\Users\YourName\Documents\My Project' ``

  • cd 在 PowerShell 和 macOS Terminal 中都可以切换目录：

``powershell cd 'C:\Users\YourName\Documents\My Project' ``

  • 本指南的 # 注释用于解释命令，复制时可以连注释一起执行；若遇到多行命令报错，逐行执行并先确认当前目录。
  • Git Bash 使用类 Unix 命令；PowerShell 与 Git Bash 的文件删除、复制等系统命令不完全相同。不要把 rm -rf、cat <<EOF 等 Bash 示例直接粘贴到 PowerShell。

3.3 macOS Terminal 提示

macOS 的 Terminal（终端）通常运行 zsh；较旧系统也可能使用 Bash。打开“应用程序 → 实用工具 → 终端”，或用 Spotlight 搜索“终端”。

macOS 上安装工具并验证：

git --version
gh --version

若没有 gh 且已安装 Homebrew：

brew install gh

以下是与 PowerShell 常用操作的对应写法：

操作Windows PowerShellmacOS Terminal（zsh/Bash）
进入目录Set-Location 'C:\Users\你的名字\Documents\My Project'cd "$HOME/Documents/My Project"
显示当前目录Get-Locationpwd
列出文件（包含隐藏项）Get-ChildItem -Forcels -la
查看文本文件Get-Content README.mdcat README.md
显示 SSH 公钥Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"cat ~/.ssh/id_ed25519.pub
创建简单 READMESet-Content -Path README.md -Value "# 项目名称\n\n项目简介。"printf '# 项目名称\n\n项目简介。\n' > README.md

$HOME 表示 macOS 用户主目录，通常类似 /Users/你的名字。路径写法使用正斜杠 /；路径含空格时要加引号。不要在 macOS 复制 Windows 的 C:\... 路径，也不要把 PowerShell 专用的 $env:USERPROFILE、Get-ChildItem、Set-Content 原样粘贴到 zsh。

跨平台规则：git status、git add、git commit、git push、git pull、git switch、git remote、gh auth login 等 Git/GitHub CLI 命令在两种系统上相同。路径参数尽量写成 README.md、docs/notes.md 这样的相对路径，不要把 Windows 的 .\文件名 用到 macOS。

3.4 设置提交者姓名与邮箱

Git 的作者姓名和邮箱会写入提交记录；它们是提交元数据，不是登录凭据。

git config --global user.name "你的姓名或昵称"
git config --global user.email "你的邮箱"
git config --global init.defaultBranch main
  • --global：对当前操作系统用户下的所有仓库生效。
  • --local：只对当前仓库生效，必须在仓库目录内运行。
  • 邮箱可以使用 GitHub 提供的隐私转发邮箱，避免把个人邮箱公开在提交记录中；到 GitHub Settings → Emails 查看设置。
  • 检查配置：

``powershell git config --global --list git config user.name git config user.email ``

若希望某个仓库使用不同身份，进入该仓库后运行不带 --global 的设置命令。

4. 身份验证与账号安全

4.1 推荐新手使用 gh auth login

gh auth login

按终端提示选择 GitHub.com、HTTPS 或 SSH，并按说明在浏览器中完成授权。授权后检查：

gh auth status

gh 的登录状态主要用于 gh 命令；Git 推送使用 HTTPS 还是 SSH，仍由仓库的远程地址和 Git 凭据设置决定。选择 HTTPS 时，GitHub CLI 可以协助配置 Git 凭据。

4.2 HTTPS 与 SSH 是什么？

  • HTTPS： 仓库地址以 https://github.com/ 开头。Git 认证由安全凭据管理器或已授权工具处理。
  • SSH（Secure Shell，安全外壳）： 仓库地址常为 git@github.com:用户名/仓库.git，通过一对密钥进行认证。
  • GitHub 不接受账号登录密码作为 Git HTTPS 密码。需要凭据时，应使用授权流程或 Personal Access Token（个人访问令牌，PAT）；不要把账号密码当作 PAT。

查看当前仓库使用的远程地址：

git remote -v

更改为 HTTPS 地址：

git remote set-url origin https://github.com/用户名/仓库名.git

更改为 SSH 地址：

git remote set-url origin git@github.com:用户名/仓库名.git

4.3 SSH 密钥（可选）

公钥 可以添加到 GitHub；私钥 必须只留在自己的电脑，绝不能上传、发给别人或粘贴到聊天窗口。

ssh-keygen -t ed25519 -C "你的邮箱"

按提示选择保存位置并设置密钥口令。之后查看公钥：

Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"

macOS Terminal：

cat ~/.ssh/id_ed25519.pub

在 GitHub 的 Settings → SSH and GPG keys → New SSH key 中粘贴公钥，然后测试：

ssh -T git@github.com

首次连接可能会询问是否信任 GitHub 主机；确认主机名正确后按提示操作。私钥通常为 id_ed25519（没有 .pub 后缀）；不要分享它。

4.4 PAT（个人访问令牌）安全规则

  • PAT 是可代表你执行操作的秘密凭据，应像密码一样保管。
  • 优先使用 GitHub 的 Fine-grained personal access token（细粒度个人访问令牌），只授予需要的仓库和权限，并设置有效期。
  • 不要把 PAT 写进代码、命令脚本、公开 Issue、README 或远程 URL。
  • 不建议使用 git config --global credential.helper store：它可能以明文保存凭据。
  • 如果令牌泄露，立即到 GitHub 设置中撤销并重新生成；只删除文件中的令牌不能保证它已从 Git 历史中消失。
[!CAUTION] <strong>凭据泄露时应立即撤销或轮换。</strong>不要把 PAT、验证码、恢复码或私钥粘贴到聊天工具中。

4.5 保护账号

  • 开启 GitHub 双因素认证（2FA），并安全保存恢复码。
  • 使用密码管理器保存密码和恢复信息。
  • 检查新授权的 OAuth 应用、SSH key 和 PAT，撤销不再使用的凭据。
  • 不要把验证码、恢复码、私钥、PAT 或 API key 交给 Copilot 或其他聊天工具。

5. 创建第一个 GitHub 仓库

5.1 在 GitHub 网页创建

  1. 登录 GitHub，点击右上角 + → New repository。
  2. 填写仓库名称，例如 hello-github。建议使用简短、清晰、便于输入的英文名称。
  3. 选择 Public（公开）或 Private（私有）。公开仓库的内容可能被任何人查看、克隆和保存。
  4. 可选择创建 README、.gitignore 模板和许可证。
  5. 点击 Create repository。

新手建议：如果仓库要存代码，先选择适合项目语言的 .gitignore；如果项目计划让别人使用，先了解许可证并选择合适的开源许可证。不要误把别人的代码作为自己的原创内容。

5.2 用 gh 创建空仓库

先确认已经登录：

gh auth status

创建公开仓库：

gh repo create hello-github --public

创建私有仓库：

gh repo create hello-github --private

按照提示选择是否克隆到本地、是否添加 README 等。若只创建了 GitHub 上的空仓库，之后用 git clone 下载：

gh repo clone 你的用户名/hello-github
cd hello-github

也可以使用：

git clone https://github.com/你的用户名/hello-github.git
cd hello-github

5.3 空仓库和带 README 的仓库

GitHub 创建的 README、许可证或 .gitignore 本身可能已经形成第一次提交。此时不要再把一个有独立历史的本地仓库直接推上去而不先处理两边历史。新手最简单的做法是先克隆 GitHub 仓库，再把本地文件放进克隆目录，随后正常提交和推送。

6. 已有本地文件：上传到新仓库

适用于电脑上已经有项目文件夹，想把它首次上传到自己的 GitHub。

6.1 先建 GitHub 远程仓库

在 GitHub 网站创建一个新仓库。若本地文件夹已经有内容，创建时暂时不要勾选添加 README、许可证或 .gitignore，这样 GitHub 仓库保持空白，初次推送更简单。

6.2 检查本地文件夹

把下面路径替换为你的实际路径。带空格的路径一定加引号：

Set-Location 'C:\Users\YourName\Documents\MyProject'
Get-Location
Get-ChildItem -Force

macOS Terminal 中使用：

cd "$HOME/Documents/MyProject"
pwd
ls -la

Get-Location / pwd 显示当前目录；Get-ChildItem -Force / ls -la 列出目录内容。确认这里是你打算上传的项目，而不是上一级或其他目录。

6.3 上传全新文件夹

git init
git branch -M main
git status
git add README.md
git diff --staged
git commit -m "docs: add project README"
git remote add origin https://github.com/你的用户名/仓库名.git
git push -u origin main

如果还没有 README，可先创建一个。Windows PowerShell：

Set-Content -Path README.md -Value "# 项目名称`n`n项目简介。"

macOS Terminal：

printf '# 项目名称\n\n项目简介。\n' > README.md

若项目有多个文件，先检查 .gitignore，然后可以用 git add -A 暂存所有新增、修改和删除的跟踪文件。首次上传尤其要先检查暂存内容：

git add -A
git status
git diff --staged

确认没有密码、令牌、个人隐私、缓存、依赖目录或不应该公开的文件后，再提交和推送。

6.4 命令解释

  • git init：在当前目录创建本地 Git 仓库。务必先检查当前目录。
  • git branch -M main：把当前分支重命名为 main。
  • git add README.md：暂存指定文件；git add -A 暂存所有变化。
  • git diff --staged：查看即将提交的具体内容。
  • git commit -m "..."：创建提交；-m 后面是提交说明。
  • git remote add origin URL：给 GitHub 仓库地址设置别名 origin。
  • git push -u origin main：第一次把 main 推送到 origin，并建立跟踪关系；之后通常可用 git push。

提交说明可以用中文或英文，关键是准确。例如：

docs: 添加项目使用说明
feat: 新增图片上传功能
fix: 修复文件名包含空格时的错误

6.5 已有 GitHub 仓库时上传本地文件

先克隆仓库，再复制文件进去，是更安全的初学者做法：

gh repo clone 你的用户名/仓库名
cd 仓库名

然后使用文件管理器把项目文件复制到这个目录（不要覆盖 .git 目录），再运行：

git status
git add -A
git diff --staged
git commit -m "feat: 导入项目文件"
git push

7. 日常维护：下载、修改、上传

7.1 每次开始工作

进入仓库目录。Windows PowerShell 示例：

cd 'C:\Users\YourName\Documents\仓库名'

macOS Terminal 示例：

cd "$HOME/Documents/仓库名"

确认所在位置、分支和工作状态：

pwd
git status
git branch --show-current

若当前没有自己未提交的改动，先下载远程更新：

git pull

git pull 可能整合远程的新提交。如果有未提交改动，Git 可能拒绝拉取；不要为了消除提示就运行 reset --hard，应先阅读第 11 节。

7.2 完成一组修改

编辑文件后，按这个顺序检查和上传：

git status
git diff
git add README.md
git diff --staged
git commit -m "docs: 更新安装说明"
git push

如果改动涉及多个明确文件，逐个暂存：

git add README.md src/app.js

如果你确实要纳入当前仓库的所有文件变化，可用：

git add -A
git status
git diff --staged

新手安全习惯： 不要盲目复制 git add . 或 git add -A 后立刻提交。先用 git status 和 git diff --staged 确认具体将上传哪些文件。

7.3 检查差异

git diff

显示工作区相对暂存区的改动。查看已暂存、即将提交的内容：

git diff --staged

查看当前目录状态：

git status

查看最近提交：

git log --oneline --decorate -10

7.4 确认远程连接

git remote -v

输出中的 origin 是远程别名，后面是 URL。若地址错误：

git remote set-url origin https://github.com/正确用户名/正确仓库名.git

8. 文件操作：新增、修改、重命名、删除

8.1 新增文件

在文件管理器或编辑器中创建文件，然后：

git status
git add notes.md
git diff --staged
git commit -m "docs: 添加笔记"
git push

8.2 修改文件

编辑并保存之后：

git diff
git add README.md
git diff --staged
git commit -m "docs: 修正项目说明"
git push

8.3 删除文件并同步到 GitHub

用 Git 删除文件，Git 会记录删除动作：

git rm old-file.txt
git status
git commit -m "chore: 删除旧文件"
git push

删除目录及其被 Git 跟踪的内容：

git rm -r old-folder

也可以先在文件管理器里删除，再使用 git add -A 记录删除。仅在电脑上删除文件不会自动删除 GitHub 上的文件；需要提交并推送删除记录。

8.4 重命名或移动

git mv old-name.txt new-name.txt
git mv notes.txt docs/notes.txt
git status
git commit -m "refactor: 整理文档位置"
git push

Git 根据文件内容相似度在历史中识别重命名；Git 本身记录的是内容变化。

8.5 只让 Git 不再跟踪文件，但保留电脑上的文件

git rm --cached local-settings.json

对目录可加 -r。如果该文件不应再次提交，还要把相应路径添加到 .gitignore。这只会影响之后的提交，不会把它从过去的提交历史中抹掉；若里面曾有凭据，应立即撤销或轮换凭据。

8.6 删除 GitHub 上的整个仓库

删除仓库与删除单个文件不同，可能影响协作者且不一定容易恢复。必须是仓库管理员或拥有相应权限的人：

  1. 打开仓库网页。
  2. 进入 Settings → General → Danger Zone → Delete this repository。
  3. 仔细阅读提示并确认仓库名称。

如只想清理内容而保留仓库，优先逐项删除文件、提交并推送；这仍会把旧内容留在 Git 历史中。执行破坏性操作之前先确认是否需要备份。

9. 分支与 Pull Request 协作

9.1 为什么用分支？

分支（branch） 让你可以在不直接改动主线的情况下完成一项工作。新手推荐：

更新 main → 创建工作分支 → 修改并提交 → 推送分支 → 创建 PR → 检查并合并

这样可以在合并前查看差异，也能让协作者审查改动。

9.2 创建、切换和查看分支

git branch
git switch -c docs/improve-guide

git switch -c 创建并切换到新分支。之后确认：

git branch --show-current

切换回主分支：

git switch main

查看本地与远程分支：

git branch -a

9.3 将分支推送到 GitHub

git add -A
git diff --staged
git commit -m "docs: 改进操作指南"
git push -u origin docs/improve-guide

-u 让本地分支关联远程同名分支；后续在此分支通常可直接 git push 和 git pull。

9.4 创建 PR 并合并

Pull Request（PR，拉取请求） 是请求审查并合并改动的页面。用网页：

  1. 推送分支后，打开仓库页面，点击提示中的 Compare & pull request；也可以进入 Pull requests → New pull request。
  2. 确认 base 是要接收改动的目标分支（通常是 main），compare 是你工作的分支。
  3. 标题简洁描述改动；正文说明做了什么、为什么做、如何验证。
  4. 创建 PR；检查文件差异、自动检查结果和评论。
  5. 按评论修改同一分支并再次 git push，PR 会自动更新。
  6. 获得批准并满足规则后，使用页面允许的合并方式合并。
  7. 确认合并完成后，可删除已合并的工作分支。

用 gh 创建 PR：

gh pr create

按提示填写标题、正文和目标分支。常见命令：

gh pr status
gh pr list
gh pr view
gh pr checks

Review（审查） 是对代码或文档改动的检查；合并权限和审批要求由仓库设置决定。

9.5 删除已合并分支

删除本地分支：

git switch main
git branch -d docs/improve-guide

删除 GitHub 上的远程分支：

git push origin --delete docs/improve-guide

-d 会保护尚未合并的分支。-D 会强制删除，可能让未合并提交难以找到；除非确认不需要，不要使用。

10. 克隆、Fork、复制和迁移别人的项目

用户说“把别人的库搬到自己账号”，可能指不同事情。先明确目标：是本地查看、参与贡献、在自己账号保留关联副本，还是建立全新的独立仓库？

10.1 Clone：只下载到电脑

git clone https://github.com/作者名/项目名.git
cd 项目名

克隆会在电脑上建立一个本地副本，通常包含完整 Git 历史。它不会自动在你的 GitHub 账号下创建仓库。是否能克隆取决于项目可见性和你的访问权限。

10.2 Fork：在 GitHub 账号下建立关联副本

在原仓库页面点 Fork，选择自己的账号。也可以用：

gh repo fork 作者名/项目名

Fork 会在 GitHub 上创建一个与你账号关联的副本，通常用于向原项目贡献改动。若要在本地工作：

gh repo clone 你的用户名/项目名
cd 项目名
git remote -v

通常 origin 指向你的 Fork；原仓库是上游。若没有 upstream，添加它：

git remote add upstream https://github.com/作者名/项目名.git

从原仓库获取更新并合并到本地 main：

git fetch upstream
git switch main
git merge upstream/main
git push origin main

如果原仓库默认分支不是 main，先到其网页确认实际分支名，并替换命令中的 main。不要在未确认本地改动状态时合并。

10.3 参与开源贡献的标准步骤

  1. 阅读原项目的 README、LICENSE、CONTRIBUTING、行为准则和 Issue。
  2. Fork 原仓库并克隆自己的 Fork。
  3. 创建工作分支：

``powershell git switch -c fix/typo-in-readme ``

  1. 只做范围清楚的修改，运行项目要求的检查。
  2. 检查、提交并推送：

``powershell git status git diff git add README.md git diff --staged git commit -m "docs: fix README typo" git push -u origin fix/typo-in-readme ``

  1. 对原作者的仓库创建 PR。目标仓库是原项目，来源分支是你的 Fork 分支。
  2. 按维护者反馈修改，等待审查和合并。

10.4 原样复制到自己账号：先理解授权和署名

“原封不动搬过来”不只是 Git 操作。能公开访问不等于可以任意去掉作者信息或许可证要求。 先检查原项目的 LICENSE、版权声明和使用条款，遵守署名、保留许可证、公开衍生作品等要求。没有许可证时，不能默认可以自由复制、修改或再发布；应先取得授权或咨询专业人士。

通常有以下选择：

  • 保留关联、贡献给原项目： 使用 Fork。
  • 建立自己维护的独立副本且保留 Git 历史： 可以 Fork，或在确认授权后镜像仓库。
  • 只想保存一个文件快照、不保留历史： 下载 ZIP 或复制工作文件，再创建新仓库；保留必要的许可证与版权声明。
  • 迁移自己拥有的仓库及其协作记录： 在 GitHub 仓库设置中使用 Transfer ownership（转移所有权）等正式功能；这与普通克隆不同。

不要把他人仓库改成自己的原创项目，不要删去作者署名或许可证，也不要绕过原项目的访问权限。

10.5 用 Git 镜像复制仓库（进阶，谨慎）

镜像通常会复制 Git 引用、分支和标签，但不等于复制 GitHub 的 Issue、PR、Actions 配置权限、Secrets、讨论、Stars 或全部项目设置。仅对自己有权复制的仓库使用；必须确认新仓库为空，并仔细检查公开范围。

git clone --mirror https://github.com/来源用户名/来源仓库.git
cd 来源仓库.git
git push --mirror https://github.com/你的用户名/新仓库.git

--mirror 会推送和同步所有 Git 引用，可能覆盖目标仓库已有引用。只在空的新仓库上操作；若不确定，请用 Fork 或 GitHub 提供的 Import/Transfer 流程。

11. 冲突与安全恢复

11.1 什么是冲突？

当两个分支修改了同一段内容，Git 可能无法判断哪边正确。文件中可能出现：

<<<<<<< HEAD
当前分支的内容
=======
另一分支的内容
>>>>>>> 另一分支名称

这些标记只是冲突提示，不是最终内容。

11.2 解决合并冲突

  1. 运行 git status，确认哪些文件冲突。
  2. 打开冲突文件，理解双方修改；编辑成最终应保留的完整内容。
  3. 删除 <<<<<<<、=======、>>>>>>> 等冲突标记。
  4. 保存后检查文件内容和差异。
  5. 标记冲突已解决并完成提交：

``powershell git add 冲突文件名 git diff --staged git commit ``

  1. 如这次合并来自 git pull，之后按需 git push。

如果 Git 正在进行合并但决定放弃，可以运行：

git merge --abort

若正在进行变基，使用：

git rebase --abort

不要同时运行不匹配当前操作的 abort 命令。

11.3 撤销未提交改动

先检查：

git status
git diff

丢弃某个文件在工作区的未提交修改：

git restore -- 文件名

这会丢弃该文件未暂存的内容，通常无法通过 Git 找回。 先确认没有需要保留的修改。

取消某个文件的暂存、但保留电脑上的修改：

git restore --staged -- 文件名

11.4 撤销已提交内容

已经推送或别人可能已拉取的提交，优先使用 revert：

git log --oneline
git revert 提交ID
git push

revert 会创建一个新提交来抵消目标提交，不会删除旧提交历史。

reset 会移动当前分支指针，可能丢弃提交或未提交改动。git reset --hard 有丢失工作内容的风险，不应作为日常“修复”命令。遇到不懂的报错时先停止，不要盲目复制危险命令。

11.5 恢复与备份的基本习惯

  • 提交前查看 git status 和 git diff --staged。
  • 正在进行的重要修改可以先创建分支或复制项目备份。
  • 删除本地文件夹前确认 GitHub 远程副本可用，且重要提交已经推送。
  • git reflog 可能帮助找回最近移动过的本地提交指针，但不是远程备份，也不能保证恢复所有未提交文件。

12. GitHub 上的项目维护工作

12.1 README：让别人知道如何使用项目

README 是仓库首页说明，建议至少写清：

  • 项目是什么、解决什么问题。
  • 主要功能或截图。
  • 安装和运行步骤。
  • 配置项说明，但不要放真实密码或密钥。
  • 使用示例、已知限制、如何报告问题。
  • 许可证及贡献方式（适用时）。

Markdown（.md）是一种轻量标记语言；# 表示标题，- 表示列表，反引号用于代码。

12.2 Issue：记录问题和待办

创建 Issue 时尽量说明：

  • 标题： 明确、可搜索。
  • 背景： 发生了什么、期待什么。
  • 复现步骤： 按步骤让别人能看到问题。
  • 环境： 操作系统、软件版本等必要信息。
  • 截图或日志： 删除令牌、个人信息等敏感内容后再上传。

Issue 可以用标签分类、指派负责人并关联 PR。具体可用功能取决于仓库设置。

12.3 权限与协作者

仓库所有者可在 Settings → Collaborators（界面名称可能略有变化）添加协作者。只授予完成工作所需的最低权限。不要把个人账号密码或 token 共享给协作者。

私有仓库成员离开项目时，及时检查并撤销其访问权限。公开仓库的代码可见性不意味着他人拥有写入权限。

12.4 Actions：自动检查

GitHub Actions 可在指定事件发生时运行自动化工作流；配置文件通常放在 .github/workflows/。例如，仅让工作流在推送和 PR 时运行：

name: Basic checks
on: [push, pull_request]

jobs:
  inspect:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Show repository status
        run: git status --short

真实项目应按其语言和工具配置构建与测试步骤。工作流可以运行代码并访问授权资源；使用第三方 Action 前检查其来源和权限，不要把秘密写入 YAML。工作流所需令牌应通过 GitHub Secrets 或受控权限提供。

12.5 Tags 和 Releases：标记并发布版本

版本标签（Tag）通常形如 v1.0.0。创建附注标签并推送：

git tag -a v1.0.0 -m "Release v1.0.0"
git push origin v1.0.0

然后可以在 GitHub 网页的 Releases 页面基于该标签撰写版本说明并上传发布文件。创建版本前检查当前分支和提交，避免给错误内容打标签。

13. README、许可证、忽略文件与大文件

13.1 .gitignore：告诉 Git 哪些文件通常不应提交

.gitignore 是仓库中的忽略规则文件。例如：

# 依赖与构建产物
node_modules/
dist/

# 本地秘密和配置
.env
.env.local

# 日志与系统文件
*.log
Thumbs.db
.DS_Store

规则应按项目需要调整。不要为了“隐藏”秘密而只加 .gitignore：若文件已被 Git 跟踪，忽略规则不会自动停止跟踪。密码、令牌一旦提交过，应当作已泄露并立即撤销/轮换。

13.2 许可证与版权

许可证（License）规定他人可如何使用、修改和分发项目。公开仓库没有许可证时，不能简单理解为“大家可以随意拿去用”。如果你引用或复制别人作品，应阅读许可证并保留它要求的版权和许可声明；不确定时先取得许可或寻求专业法律建议。

13.3 大文件

Git 适合记录文本和源文件，不适合反复提交大型二进制文件。GitHub 对单文件大小和仓库使用有平台限制；大文件可能需要 Git LFS（Large File Storage，大文件存储扩展）或其他文件托管方案。先查看 GitHub 当前官方限制，不要通过拆分或改名试图绕过平台政策。

如果需要 Git LFS，先安装 Git LFS 并阅读项目说明，再跟踪相应文件类型；普通新手项目一般不需要提前配置。

14. Copilot CLI 与 GitHub CLI 的配合

14.1 先区分“问 AI”与“执行 Git”

  • Copilot CLI 适合请求解释命令、总结错误或协助编写命令。
  • git 和 gh 执行仓库与 GitHub 操作。
  • AI 给出的命令不一定适合当前目录、分支、权限或操作系统；先读懂命令和影响，再执行。

例如，可以请 Copilot CLI 解释：

请用中文解释 git status 的输出，不要运行修改文件或 Git 历史的命令。

也可以问：

我在 Windows PowerShell 或 macOS Terminal 中，如何查看当前仓库的远程 URL？请只给出只读命令并解释结果。

14.2 执行前特别检查的命令

看到以下操作时先暂停并理解影响：

  • git reset --hard：可能丢弃未提交的工作。
  • git push --force / --force-with-lease：可能改写远程历史。
  • git clean -fd：可能删除未跟踪文件。
  • git rm -r：递归删除被 Git 跟踪的目录内容。
  • git push --mirror：可能覆盖目标远程仓库引用。
  • 删除整个仓库或 .git 目录的命令。

不要把 access token、SSH 私钥、.env 文件或个人敏感数据贴给 AI。 处理仓库前，先让工具说明目标路径和将发生的更改。

[!WARNING] <strong>执行前先确认影响范围：</strong>reset --hard、强制推送、git clean -fd 和镜像推送都可能造成难以恢复的改动。

17. 从零开始的完整实战

以下示例创建一个新仓库、上传文档，再通过分支和 PR 更新它。将 你的用户名 替换成自己的 GitHub 用户名。

第一步：创建 GitHub 仓库

在网页上创建 my-first-project，选择 Public 或 Private，并添加 README。然后克隆到电脑：

gh auth status
gh repo clone 你的用户名/my-first-project
cd my-first-project
git status

第二步：添加文件

用编辑器在仓库目录创建 notes.md，写入内容并保存。检查文件状态：

git status
git diff

新文件还没有被 Git 跟踪时，git diff 不一定显示其内容；暂存后再看：

git add notes.md
git diff --staged

第三步：提交并推送

git commit -m "docs: add project notes"
git push

刷新 GitHub 仓库网页，确认文件和提交已经出现。

第四步：用分支修改

git switch -c docs/update-notes

编辑 notes.md，然后检查、提交、推送：

git status
git diff
git add notes.md
git diff --staged
git commit -m "docs: update project notes"
git push -u origin docs/update-notes

第五步：创建并合并 PR

gh pr create

按提示创建 PR。打开 PR 页面，检查目标分支、改动内容和自动检查。确认无误并满足仓库规则后再合并。合并后更新本地 main：

git switch main
git pull

这套流程覆盖了最常见的工作：克隆 → 修改 → 检查 → 暂存 → 提交 → 推送 → PR → 合并 → 更新本地。

给初学者的十条安全原则

  1. 每次操作前先确认当前目录：PowerShell 用 Get-Location，macOS 用 pwd。
  2. 不确定仓库状态时先运行 git status。
  3. 先看 git diff，再看 git diff --staged，确认将提交的内容。
  4. 只提交属于当前任务的文件，避免把整个电脑目录当成仓库。
  5. 不提交密码、PAT、SSH 私钥、.env、浏览器数据或个人文件。
  6. 不确定 reset --hard、强制推送、镜像推送的影响时，不要执行。
  7. 公开仓库中的内容可能被复制、缓存或永久留存；不要把敏感文件推上去。
  8. Fork、复制和再发布别人的项目之前，先读许可证并保留必要的署名。
  9. 遇到冲突先读 git status 和文件内容，不要为了“继续”而删除冲突文件。
  10. 把 GitHub 当作协作与备份工具之一，但重要资料仍应有独立备份。
学习目标不是背下所有命令，而是能解释命令会影响哪个目录、哪个分支、哪些文件，以及是否会改写历史。 先从安全、可检查的日常流程练起，再逐步学习高级 Git 操作。
